## 0. 一句话概括

三层各治一处：**服务端**热路径的「同步全量重写 JSON」迁 SQLite；**OSS** 建前缀分层 + 保留策略 + 配额，把无界增长变成可预算；**客户端**项目文件从单个 JSON 换成 SQLite，拿到增量保存与崩溃安全。三层互不阻塞，按 P0→P5 推进。

### 1.3 雨云 rains3 能力实测（重要，实现时必须遵守）

| 能力 | 结果 |
|---|---|

### 1.4 雨云的一个安全缺陷（已知，暂不处理）

`ListMultipartUploads` **跨租户泄漏**：任何租户调用都会返回全平台其它租户的未完成分片上传列表（含对方的文件路径、任务名、账号名、K8s/备份路径）。

- 已用 `ListParts`（返回 `NoSuchUpload` 404）+ `HeadObject`（404）+ `ListObjectsV2`（0 个）三重验证：**这些上传不在本桶、不占本桶容量、与本账号密钥无关**
- 反向影响：**我方 key 也在被他人看见** → **key 中永远不得包含用户名、项目名、任务名等可识别信息**（现有 `assets/<纯 ASCII 资产 id>` 是安全的，新布局须保持）
- Qiji 全程使用单次 `PutObject`（服务端 `ossPut` / 客户端预签名直传），**不产生分片上传**，故 `AbortIncompleteMultipartUpload` 不支持对我方无影响

### 1.5 运营量级

- 当前：内部使用，即将上线
- **峰值目标：3,000 视频/天 + 10,000+ 图片/天 ≈ 13,000 对象/天 ≈ 73 GB/天**
- 用户规模：约 500 用户 / 5 渠道商

## 3. OSS：前缀布局与 lifecycle

### 3.1 Key 布局

**新对象**（`storage='v2'`）：

```
tmp/2026/07/TP00024261.png          临时/上传素材
img/2026/07/C00037030.png           五类资产图（C/A/G/M/S/P）
video/2026/07/video00023247.mp4     视频
audio/2026/07/audio00002156.mp3     音频
thumb/2026/07/C00037030.webp        缩略图 256px（约 30KB）
```

**老对象**（`storage='legacy'`）：保持 `assets/<id>.<ext>` 扁平布局，**原地不动，永不迁移**。

分年月的三个理由：① lifecycle 可做到月粒度；② 单前缀对象数不会涨到千万级（控制台列举不至于卡死）；③ 按月统计容量只需列一个前缀。

> ⚠ **key 中禁止出现用户名 / 项目名 / 任务名**（见 §1.4）。

### 3.2 lifecycle 的定位：只做兜底安全网

因为 TP 改走引用判定（决策 10），**lifecycle 不再承担任何常规清理职责**：

| 规则 | 用途 |
|---|---|
| `tmp/` 前缀 **180 天**无条件过期 | 兜底：万一服务端清理任务长期失效，防止无限堆积 |

**所有常规清理（含 TP）一律由服务端定时任务执行**，因为 lifecycle 只能按「前缀 + 天数」判断，**无法判断「是否被引用 / 是否被收藏」**。

### 3.3 lifecycle 下发的实现要点

```js
// 1. 必须补 Content-MD5（rains3 用老式 S3 校验语义）
client.middlewareStack.add((next) => async (args) => {
  const r = args.request;
  if (r?.body && !r.headers["Content-MD5"])
    r.headers["Content-MD5"] = createHash("md5").update(r.body).digest("base64");
  return next(args);
}, { step: "build", name: "addContentMd5" });

// 2. 下发后必须 Get 读回逐条校验（子项会被静默丢弃）
// 3. 不要使用 AbortIncompleteMultipartUpload（不支持）
```

## 4. 保留与清理规则

### 4.1 判定模型

```
有收藏（用户收藏 或 平台收藏）  →  永久保留
取消收藏                        →  把 last_ref_at 刷成当前时刻 → 落入「被引用」档
被引用过（last_ref_at 有值）    →  last_ref_at + ref 天
从未被引用（last_ref_at 为空）  →  created_at  + unref 天
```

**TP 与正式资产走完全相同的规则**（决策 10），仅 key 前缀不同。

```jsonc
// settings.json，管理端可调
"retentionDays": { "unref": 7, "ref": 14 }
```

### 4.2 清理任务的 SQL

```sql
SELECT id FROM assets
WHERE purged_at IS NULL
  AND id NOT IN (SELECT asset_id FROM favorites)
  AND id NOT IN (:共享库素材 id 集合)          -- shared-libs.json，内存 Set
  AND ( (last_ref_at IS NOT NULL AND last_ref_at < :now - :refDays * 86400)
     OR (last_ref_at IS NULL     AND created_at  < :unrefCutoffIso) )
```

> ⚠ **类型陷阱（P0 实现时发现）**：`last_ref_at` / `purged_at` 是 INTEGER（epoch 秒），
> 但既有的 **`created_at` 是 TEXT ISO 串**（`2026-07-30T12:00:00.000Z`）——两者不能混着比。
> `created_at` 必须与 **ISO 串**比较（`:unrefCutoffIso = new Date(now - unrefDays*86400e3).toISOString()`）；
> ISO 串字典序即时间序，且能走 `idx_assets_created` 索引。写成 `created_at < :now - N*86400` 会恒为 false（字符串 vs 数字），**清理任务会静默不清任何未引用资产**。

清理动作 = `ossDelete(key)` + `UPDATE assets SET purged_at = :now`。**台账行永不删除**（见 §4.4）。

### 4.3 引用上报（`last_ref_at` 的唯一来源）

客户端在**打开项目**与**保存项目**时，各上报一次本项目引用的资产 id 集合：

```
POST /v1/assets/ref   { assetIds: ["C00037030", "video00023247", ...] }
→ 服务端 UPDATE assets SET last_ref_at = now WHERE id IN (...)
```

> ⚠ **必须在「打开项目」时也上报**。只在保存时上报的话，用户只是打开看看没改动的项目，其素材会被误清。

### 4.4 为什么台账行必须软删除（关键约束，勿违反）

`reputAsset()`（死链自愈重传）第一行就是查台账：

```js
const rec = getAsset(id);
if (!rec) return undefined;   // 台账行没了 → 自愈永久失效
```

**删台账行 = 那个资产再也救不回来**，哪怕用户本机原件还在。因此：
- 死记录 / 已清理对象 → 标 `purged_at`，**行保留**（181 字节/行，10,813 行仅 2MB）
- 用户「检查素材」→ 探活失败 → `reput` 用本地字节重传 → **成功复活**，顺手清 `purged_at`

同理，**孤儿对象要补台账而不是删对象**：它们是直传流程漏单（客户端已上传成功并把 url 记进了 `assetBlobs`，只是服务端 `complete` 没调到），用户项目里可能正引用着。

## 5. 服务端数据结构

### 5.1 `assets` 表改造（只加列、只加索引，不动任何老列）

```sql
ALTER TABLE assets ADD COLUMN storage      TEXT;     -- 'legacy' | 'v2'
ALTER TABLE assets ADD COLUMN size_bytes   INTEGER;  -- 容量统计与配额的基础
ALTER TABLE assets ADD COLUMN user_id      TEXT;     -- 归属用户
ALTER TABLE assets ADD COLUMN agent_id     TEXT;     -- 归属渠道商（冗余，便于成本归因）
ALTER TABLE assets ADD COLUMN last_ref_at  INTEGER;  -- 最后被引用（epoch 秒）
ALTER TABLE assets ADD COLUMN purged_at    INTEGER;  -- OSS 对象已清理（软删除墓碑）
ALTER TABLE assets ADD COLUMN has_thumb    INTEGER;  -- 0/1 缩略图是否已生成

CREATE INDEX IF NOT EXISTS idx_assets_created ON assets(created_at);
CREATE INDEX IF NOT EXISTS idx_assets_user    ON assets(user_id, created_at);
CREATE INDEX IF NOT EXISTS idx_assets_sweep   ON assets(purged_at, last_ref_at);
CREATE INDEX IF NOT EXISTS idx_assets_type    ON assets(type, created_at);
```

> 决策记录：**曾考虑去掉冗余的 `url` 列以省体积（约减半），已否决** —— 850MB/年 对 SQLite 不构成问题，而重建表有迁移风险。收益假、风险真。

### 5.2 存储档（storage profile）

```jsonc
// settings.json
"storageProfiles": {
  "legacy": { "endpoint": "…", "bucket": "jianqiji-qiji", "publicBase": "…",
              "layout": "flat",           "writable": false },
  "v2":     { "endpoint": "…", "bucket": "jianqiji-qiji", "publicBase": "…",
              "layout": "kind/yyyy/mm",   "writable": true, "active": true }
}
```

`url` / `oss_key` 由 `storage + id + ext + created_at` 推导；`oss_key` 列保留为**例外通道**（非空时优先使用）。

**必须同步修改的代码点**：

| 位置 | 现状 | 改为 |
|---|---|---|
| `reputAsset()` | 沿用 `rec.ossKey` 原样重传 | 按该行的 `storage` 档重新生成 key（否则自愈出来的对象会顶着老 key 落在新前缀之外，逃过所有规则） |
| `ossDelete()` | 用当前配置的桶 | 按行的 `storage` 档定位 |
| `ossPresignPut()` | 用当前配置的桶 | 用 `active` 档 |
| `assetUrl()` | 返回存的 `rec.url`（✅ 已正确，换布局后老对象照常可访问） | 不变 |

### 5.3 `favorites` 表（新）

```sql
CREATE TABLE favorites (
  asset_id   TEXT NOT NULL,
  owner_type TEXT NOT NULL,              -- 'user' | 'platform'
  owner_id   TEXT NOT NULL DEFAULT '',   -- 平台收藏为空串
  created_at INTEGER NOT NULL,
  PRIMARY KEY (asset_id, owner_type, owner_id)
);
CREATE INDEX idx_fav_owner ON favorites(owner_type, owner_id, created_at);
```

语义：
- **多人收藏取并集** —— 只要还有一条记录就永久保留
- **平台收藏（管理端二次收藏/审核）优先级最高** —— 用户全取消，平台收藏还在就保留
- **删用户 → 级联删其 favorites** → 若该资产再无人收藏，转入 +14 天倒计时（**绝不立即删**）
- **取消收藏绝不立即删**，一律刷 `last_ref_at` 转入倒计时
- 用量**实时 SUM**（`favorites JOIN assets`），不做计数器（计数器不同步是经典 bug；10 万行带索引求和是微秒级）

> ⚠ 客户端现有收藏（`localStorage` 的 `Qiji:favoriteAssets`）是**按 uri 匹配**的，换机即失效、服务端完全不知情。必须改为**按 assetId** 并落服务端。

### 5.4 配额与扩容卡

```jsonc
// settings.json（管理端可调）
"favQuotaBytes":     209715200,    // 个人收藏 200 MB
"teamLibQuotaBytes": 2147483648,   // 团队共享 2 GB
"storageCode": {
  "user": { "bytes": 209715200,  "days": 30, "price": 300  },   // 个人扩容卡
  "team": { "bytes": 1073741824, "days": 30, "price": 1000 }    // 团队扩容卡
}
```

- `User.favQuotaBytes?` —— 按用户覆盖
- `Team.libQuotaBytes?` —— 按团覆盖
- **生效配额 = 基础配额 + SUM(未过期的 quota_grants)**

```sql
CREATE TABLE quota_grants (
  id         TEXT PRIMARY KEY,
  owner_type TEXT NOT NULL,      -- 'user' | 'team'
  owner_id   TEXT NOT NULL,
  bytes      INTEGER NOT NULL,
  code       TEXT,               -- 核销的卡号
  granted_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);
CREATE INDEX idx_grant_owner ON quota_grants(owner_type, owner_id, expires_at);
```

**扩容卡**（`storage-codes.json`，与 `redeem-codes.json` / 团队码同构，**保留 JSON**）：

```jsonc
{ "code": "sc-a1b2c3d4", "target": "user" | "team",
  "bytes": 209715200, "days": 30,
  "agentId": "ag_xxx",                      // 签发渠道商（开码积分实扣归属）
  "usedBy": { "type": "user", "id": "u_x" }, "usedAt": "…", "createdAt": "…" }
```

- 渠道商在门户签发，**从开码积分实扣**（与团队码完全同构，复用现成链路）
- 用户/团长在客户端核销 → 写入 `quota_grants`
- 未核销可作废（无退回，与激活码同规则）
- 管理端「配额」页可见：谁买了、多少、何时到期

**两条待定规则（先按推荐值实现，管理端可改）**：
1. **多张卡叠加**：容量叠加、各自独立计时（买两张 = +400MB，第一张到期后回落 +200MB）
2. **到期后超额**：7 天宽限期，期间只禁新增收藏、不删任何东西；超期后按「最早收藏优先」自动取消到配额内（被取消的走 +14 天倒计时）

> **配额的本质是「永久保留额度」，不是「存不下」。** 超额提示应为「收藏空间已满，请清理或使用扩容卡」，用户仍可正常生成和使用。

### 5.5 迁 SQLite vs 保留 JSON

| 迁 SQLite | 理由 |
|---|---|
| `assets`（已在）· `favorites` · `quota_grants` | 量大、要索引查、要 JOIN 求和 |
| `logs` + `log_details` | 写最频、量最大、查询最复杂；顺带解决 39 万个详情文件的扁平目录 |
| `users` + `agents` | 热路径同步全量重写；进同一事务解决「扣了用户没扣渠道商」 |
| `tasks` | 写频量小，最后迁 |

| **保留 JSON**（不迁，勿为统一而统一） |
|---|
| `models` `templates` `presets` `channels` `modes` `families` `settings` `protocols` `teams` `shared-libs` `redeem-codes` `storage-codes` `agent-groups` |

理由：启动读一次、偶尔写，**可读、可 diff、可手工抢救**。线上出事能 `cat` 一眼、改一行救回来。

### 5.6 服务端性能问题的定位（迁移的动因）

已确认的三处「越用越卡」（用户实测特征：**早上顺、越到晚上越卡、过零点恢复**，已验证吻合）：

1. **`logs-index/<当天>.jsonl` 每次 flush 全量重写**：13,000 条/天 × 300B ≈ 4MB，日内单调增长，`JSON.stringify` 13k 对象每次阻塞主线程 20–50ms，防抖窗口 1 秒 → 晚上每秒卡一次
2. **`data/logs/` 扁平目录 39 万文件**（13k/天 × 30 天保留），且**启动时 `sweepOrphanDetails` 要 readdir 整个目录** → 启动慢
3. **热路径同步全量重写**（`routes.ts` `applyBilling`）：每个生成请求 → `chargeCreditsAs()` 写 `users.json` + `changeAgentCredits()` × 链级数 写 `agents.json`，全部是同步 `writeFileSync`
4. 附带：全部日志 meta 常驻内存（一年 475 万条 ≈ 1.4GB）、`getUserByAccessKey` 是数组线性扫描

### 5.7 备份规则（迁移后必须改）

**正在写的 `.db` 不能直接 `cp`**。用 `VACUUM INTO 'backup.db'`（SQLite 原生、在线安全）或 `sqlite3 .backup`。备份 `qiji.db` 时必须连 `-wal` / `-shm` 一起，或先 checkpoint。

## 6. 缩略图

- 规格：**256px WebP，约 30KB**，key `thumb/yyyy/mm/<id>.webp`
- 生成方：**客户端**（复用 `assetPersist.ts` 已有的 `ensureThumb` canvas 降采样逻辑），经现有直传通道上传
- 台账 `has_thumb` 标记是否已生成
- **原图分毫不动**，缩略图是额外的小文件
- 必要性：素材库一页 50 张原图 = 170MB 流量，翻十页 1.7GB。没有缩略图，素材库上线即流量失控

## 7. 客户端项目文件

```
项目文件夹/
├─ project.qiji            ← SQLite（表：meta / assets_ref / episodes / shots /
│                             canvases / nodes / edges / commits / pending）
├─ project.qiji-wal
└─ assets/<资产id>.<ext>   ← 字节仍在旁边，绝不进 BLOB
```

**收益**：增量写（只 UPDATE 变动行）、事务 + WAL 崩溃安全（根治「三姐妹 161MB」「锁妖塔 38MB」两起截断损坏）、局部加载、不必自造 manifest 两阶段提交。

**为什么不是多 JSON 文件树**：现在一次 rename 就是原子一致快照；拆成 N 个文件后崩在中间会得到半新半旧的组合，要挡住必须 manifest + version/sha + 两阶段提交 —— 那就是在手写事务引擎。

**导出**：
- 完整包 = `zip(project.qiji + assets/)`，走 **Rust 侧流式**（大项目视频 GB 级，jszip 在 WebView 里会内存爆；`jszip` 已在依赖中且从未使用，可用于轻量包）
- **轻量包** = 只含 `project.qiji` + **资产 id 清单**；导入时先上报清单（顺带刷 `last_ref_at`）并检查存活，**缺失的明确列出是哪几个**，而不是打开后一片裂图
- 包内带版本号 + 各文件 sha

**改造入口**（已收敛得较窄）：`projectStore.save` / `loadFromPath` / `debouncedSave` 三处。先抽持久化接口，再换底。

## 8. 容量测算

峰值 73 GB/天（视频 39 GB + 图片 34 GB），按本方案稳态：

| 档位 | 稳态容量 |
|---|---|
| 未引用 7 天（含 TP） | ~510 GB |
| 被引用 14 天（活跃项目持续续期） | 440 GB ~ 1 TB |
| **收藏永久（有硬顶）** | 500 用户 × 200MB = 100 GB<br>+ N 团队 × 2GB<br>+ 扩容卡售出量 |
| **Qiji 桶合计** | **约 0.7 ~ 1.2 TB** |
| 用户其它桶 | 0.7 TB |
| **账号总计** | **1.4 ~ 1.9 TB，2TB 套餐内** |

**关键结构性改善**：永久保留档从「无界」变成「配额之和」，可精确预算，扩容卡卖多少就多增多少。

**流量**：入免费；出 73GB/天 ≈ 2.2TB/月，4TB 套餐够用（缩略图是流量的关键保障）。

**配额换算提醒**（按实测均值）：

| | 200 MB 能装 | 2 GB 能装 |
|---|---|---|
| 图片 @3.4MB | **约 59 张** | 约 590 张 |
| 视频 @12.99MB | **约 15 个** | 约 158 个 |

用户已确认**按容量计**（非张数）。视频特别吃配额，UI 需明确提示。

## 9. 存量特赦（首次上线必做）

**问题**：`last_ref_at` 初始全空 → 存量一律落「未引用 7 天」档 → 实测**会一次性清掉 90,697 个 / 397.87 GB（78.4%）**，只剩约 110 GB。这些是真实用户的历史素材，直接开规则是产品事故。

**方案（两个旋钮，都是配置，随时可中止）**：

```
清理功能上线当天：
  1) 把全部存量资产 last_ref_at = 上线日   → 全体落入「被引用」档
  2) retentionDays.ref 临时设为 30，一个月后调回 14
```

- 上线后 30 天内不动任何存量资产（实测 30 天档只会清 5.3GB，等于不动）
- 这 30 天里用户陆续打开项目 → 引用上报 → 活跃素材自动续期
- 30 天后调回 14 天，没人打开过的存量才被清 —— 那时已是「确认没人要」

**首次清理必须分批**：先只清 `tmp/`，观察无用户投诉后再动正式资产。**不要一次删 400GB。**

## 10. 分阶段实施

### P0 · 存储对账与台账改造（纯服务端，客户端零改动，可回滚）

1. `assets` 加 7 列 + 4 索引（`ALTER TABLE ADD COLUMN` 瞬时、不阻塞）
2. storage profile 落地；**修 `reputAsset` / `ossDelete` / `ossPresignPut` 按档定位**
3. **回填 `size_bytes`**：全量 `ListObjectsV2` 一遍（约 11 万对象，几分钟）
4. **孤儿补台账**：从 key 反推 id/type/ext，`LastModified` 作 `created_at`
5. **死记录标 `purged_at`**（10,813 条，行保留）
6. 管理端「存储」页：容量 KPI（按类型/用户/月份）+ **对账按钮**

> **对账脚本必须部署到服务器上、对实时台账跑。** 在本地对静态快照跑会把「快照之后新产生的正常对象」误判成孤儿。
> 交付三个脚本，默认 `--dry-run`：`migrate-p0.mjs`（加列建索引，幂等）· `reconcile.mjs`（回填/标记/补账）· `verify.mjs`（校验台账 ↔ 桶一致）

### P1 · 引用、收藏、配额（服务端 + 客户端小改动，需发版）

1. **引用上报**：客户端打开项目 + 保存项目各上报一次 → `last_ref_at`
2. **收藏服务端化**：改按 assetId + `favorites` 表 + 个人 200MB 配额
3. **缩略图**：客户端生成 256px WebP，直传 `thumb/` 前缀
4. **团队共享配额 2GB** + **扩容卡**（门户签发 / 客户端核销 / `quota_grants`）
5. 管理端收藏与配额管理界面（按用户/类型/占用容量排序，支持平台收藏）

### P2 · 观察期 ≥30 天（**只统计，不删任何东西**）

管理端显示「按当前策略将清理 N 个 / X GB」，人工核对合理性。**这一步不能省。**

### P3 · 清理上线

1. `tmp/` 前缀挂 lifecycle **180 天**（仅兜底安全网）
2. 常规清理任务上线，**先 dry-run 一周**，人工确认后开真删
3. 按 §9 存量特赦执行；首次分批
4. 清理 = `ossDelete` + 标 `purged_at`，**台账行永不删**

### P4 · 服务端热路径迁 SQLite

`logs` + `log_details` → `users` + `agents`（同事务计费）→ `tasks`。解决 §5.6 的四个问题。

### P5 · 客户端项目文件

`project.qiji` 换 SQLite + 分域增量保存 + zip 导出（含轻量包）+ **存量项目迁移器与回退路径**。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 观察期不足就开删 | 硬性 ≥30 天 + dry-run 一周 + 存量特赦 + 首次分批 |
| 收藏率超预期 | 配额是硬闸；管理端收藏页按占用排序便于审核 |
| 跨机 / 共享库 / 轻量包素材被清 | 收藏与共享库素材永久保留；轻量包导入时主动检查并列出缺失 |
| **7/14 天下「跨设备可用」≈「有没有收藏」** | 收藏按钮文案必须写明「收藏后云端永久保留，可跨设备打开」 |
| 峰值上量后 2TB 不够 | 管理端容量 KPI 做阈值告警，提前一个月能看出趋势 |
| 客户端 SQLite 重构 | 入口已收窄至三处；先抽接口再换底；带迁移器与回退 |
| 删台账行断掉自愈 | **硬性约束：台账行只软删除**（§4.4） |

## 12. 遗留未决（不阻塞实施）
