# Qiji 2.0 设计需求草案

> 状态：讨论中。本文记录已经提出、但尚未完成详细设计和验收定义的 Qiji 2.0 需求；不得据此推断已经实现。

## 文本模型按 Token 计费

### 背景

Qiji 2.0 计划采用“总编排器 → 专业身份 → Skill → Knowledge / MCP Tool”的 AI 协作架构。一个用户目标可能被拆成多个较小的文本模型步骤；继续按请求次数收取相同固定费用，无法准确反映不同步骤的上下文规模、输出长度和实际成本。

### 已确认方向

- 文本模型从“每次请求固定收费”调整为“按实际 Token 用量计费”。
- 身份编排产生的各个文本模型步骤分别计量，最终聚合为用户任务的总用量和总费用。
- 图片、视频、音频等非文本生成的计费方式不在本条需求中改变，后续分别设计。
- 计费结果应可解释，至少能够追溯到模型、步骤、输入 Token、输出 Token、单价和最终金额。

### 待详细讨论

- 输入、输出、缓存命中、推理 Token 和平台注入上下文分别如何计价。
- Skill 正文、平台知识、项目知识和用户知识产生的上下文成本由谁承担、如何展示。
- 上游返回 usage 缺失或不可信时，采用何种 Token 估算与对账方式。
- 流式中断、用户取消、模型失败、工具调用失败和重试的收费规则。
- 预估费用、预算上限、预授权、最终结算、退款与幂等事务设计。
- 多身份并行、子步骤重试及验证步骤如何聚合，避免重复扣费。
- 平台成本价、用户售价、渠道商价格、会员折扣和舍入精度。
- 用户端应展示单步骤明细，还是默认展示任务汇总并允许展开。

### 设计约束

- 不能仅依赖客户端上报 Token；服务端必须拥有可验证的计量依据。
- 计量、扣费、退款和任务状态需要具备原子性与幂等性。
- 编排器必须支持任务级 Token / 金额预算，防止多步骤执行失控。
- 检索应遵循“索引找详情、只加载必要内容”，避免无价值的上下文注入增加用户成本。
