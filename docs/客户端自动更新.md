# 客户端自动更新

从 v2.0.1 开始，桌面客户端启动 15 秒后检查更新，此后每 4 小时检查一次；标题栏「检查更新」可随时手动检查。开发环境不会自动检查，浏览器版隐藏更新入口。

发现更高版本会自动下载并校验签名，完成后提示「保存并重启安装」。选择「稍后」可继续工作，本次进程保留已下载包。关闭程序后，下次启动重新检查和下载。安装前保存当前项目；保存失败、正在生成/分析/上传、编辑弹窗未提交、其他窗口仍打开时暂停。Windows 使用 Tauri 的 passive 更新安装并重新打开应用，沿用 `Qiji` / `com.qiji.canvas` 标识。

旧 v2.0.0 不含更新模块，需要手动安装一次 v2.0.1 或更高版本作为入口；客户端功能、后台发布代码、发布清单和设备验收是独立状态，见 `docs/memory/ACTIVE.md`。

## 正式打包

1. 双击项目根目录的 `打包可分享应用.bat`，或兼容入口 `打包成可分享文件.bat`。默认补丁号加一，例如 `2.0.2 → 2.0.3`、`2.0.9 → 2.0.10`；脚本自动同步 package、npm锁文件、Tauri配置、Cargo清单及锁文件。配置版本不一致则先报错，不改文件。大版本更新时再按用户要求修改BAT中的 `QIJI_VERSION_INCREMENT`，日常保持 `patch`。
2. BAT调用 `scripts/package-client.ps1`；直接执行 `pwsh -NoProfile -File scripts/package-client.ps1 -NoOpen` 同样默认加一。基础环境校验后递增版本，再执行前端检查、完整测试、正式构建、签名生成以及内置公钥验签。打包失败后已递增的版本号保留，下次继续加一；同一项目并行打包会被拒绝。
3. 同一个 `release/Qiji-版本-时间/` 目录内自动生成 NSIS `.exe`、MSI `.msi`、各自 `.sig`、`update-release.json`、`SHA256SUMS.txt`、`build-info.json`、`更新说明.txt`和`推送更新步骤.txt`。推送前在更新说明中补充本次实际更新内容。自动更新入口发布 NSIS `.exe`，打包本身不会上传或推送。

签名私钥在本机 `%USERPROFILE%\.tauri\qiji-updater.key`，不在仓库/安装包/服务端中。默认打包脚本自动读取；其他机器可从安全备份恢复，或设置 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。初始本机密钥为无口令密钥，已限制文件访问权限。须另行保存安全备份，未来更新继续使用同一签名密钥，不能临时重新生成。源码只包含公钥。

## 后台发布

源站部署本轮服务端代码后，打开管理端「网页管理 → 客户端自动更新」，选择同一次打包目录中的 `update-release.json` 与 `.exe`，填写更新说明，然后点击「上传、验签并发布更新」。

安装包凭现有管理员鉴权签发的预签名 URL 直传 OSS。服务器流式验证安装包与 Tauri 签名、密钥身份和版本递增，通过后先写版本历史，再原子替换稳定更新清单，并保存本地上一份清单。错签名、被篡改或缺失的安装包均拒绝发布；渠道节点不注册发布接口。官网展示下载链接与客户端更新清单独立管理。

- 固定 HTTPS 清单：`https://jianqiji.cn-sy1.rains3.com/site/updates/stable.json`。
- 安装包：同域 `site/pkg/*.exe`，每次上传不同对象名。
- 历史清单：`site/updates/history/<version>.json`。
- 源站状态：`data/client-update.json`；上次状态：`data/client-update.previous.json`。

换资产桶时仍要保留更新清单对应的可写存储档和原 HTTPS 地址。发布代码按固定地址查找存储档，不随资产的 active 档切换。客户端保持 HTTPS 与强制验签；不启用不安全传输或版本降级。清单损坏时可恢复之前的清单停止继续推送；已升级用户需通过更高版本的修复包恢复功能。

## 验证范围

专项自动测试覆盖下载/安装顺序、重复点击、签名篡改、保存失败、窗口与任务保护。隔离 UI 验证使用模拟更新传输及安装端口，真实渲染更新提示，不能代替 Windows 设备上的覆盖安装验收。设备验收须确认项目、登录、素材、上传及多窗口行为，并验证从一版到更高一版的完整更新。
