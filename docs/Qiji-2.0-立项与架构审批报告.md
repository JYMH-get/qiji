# Qiji 2.0 立项与架构审批报告

> 本报告已于 2026-08-28 获得用户审批与开工授权；勾选项为本次获批范围，后续重大变更继续通过本报告或 ADR 审批。

## 1. 执行摘要

Qiji 1.x 保持现有生产运行，在较长时间内只承担必要维护；Qiji 2.0 作为独立项目重新设计和实现，不以兼容旧代码、旧数据库或旧项目文件为默认目标。

Qiji 2.0 的目标不是简单重写界面，而是同时完成三项升级：

1. 工程升级：清晰领域边界、唯一业务入口、运行时契约、自动测试、持续集成、安全默认值与性能预算。
2. 产品升级：降低首次成功门槛，强化项目确定感、失败恢复、素材复用、工作流复用和创作效率。
3. AI 升级：以身份编排、Skills、分层知识和 MCP 工具组成可执行、可学习、可治理的 AI 创作助手。

## 2. 项目边界

### 建议方向

- Qiji 1.x 与 Qiji 2.0 使用独立 Git 仓库、依赖、数据库、部署和发版流程。
- Qiji 1.x 的代码、测试、事故记录和运维经验是需求证据，不作为 Qiji 2.0 的运行时依赖。
- Qiji 1.x 冻结普通功能，只处理必要安全修复和生产故障。
- Qiji 2.0 默认不兼容旧 `.Qiji` 文件；如商业上确有需要，后续单独设计一次性导入器。
- 不复制旧模块后改名。先提炼领域规则、行为样例和验收测试，再实现新模块。

### 非目标

- 不以短期实现全部 1.x 功能为目标。
- 不提前建设微服务体系。
- 不为尚未出现的渠道或工作流设计万能抽象。
- 不让新旧两套同类实现长期并存。
- 不以减少代码行数代替可理解性、正确性和性能。

## 3. 产品目标

### 核心用户

待审批的优先顺序：

1. 小型创作团队与工作室。
2. 个人漫剧创作者。
3. 商业渠道商及更大规模团队。

### 核心用户旅程

第一条完整闭环建议为：

`创建项目 → 导入/创作故事 → 建立角色与场景资产 → 生成分镜 → 生成媒体 → 编辑时间线 → 保存重开 → 导出交付`

### 产品成功指标

- 新用户首次成功生成作品所需时间。
- 项目保存、关闭和恢复成功率。
- 生成失败后的可恢复率。
- 完成一集所需操作次数与等待时间。
- 画布、时间线和项目打开的交互延迟。
- 7 日留存、项目完成率与 AI 建议采纳率。
- 崩溃率、任务失败率与退款对账差异。

### 体验原则

- 默认简单，高级能力渐进展开。
- 所有结果可追溯，所有失败可恢复。
- 自动保存和后台任务始终提供明确状态。
- 重要写操作可预览、可确认、可撤销。
- 模板与工作流可以复用，不要求用户重复劳动。
- 统一设计系统、快捷键、术语和错误表达。

## 4. 领域模型

建议划分为七个核心领域：

| 领域 | 核心职责 |
| --- | --- |
| 项目 | 剧本、分集、分镜、时间线、画布与项目生命周期 |
| 资产 | 角色、场景、生物、物品、声音及媒体文件 |
| 生成 | 意图、参数、任务、进度、结果、取消与失败恢复 |
| 渠道 | 模型目录、能力、协议翻译、路由与健康状态 |
| 账户 | 用户、团队、权限、套餐和配额 |
| 计费 | 估价、预算、预授权、实扣、退款和对账 |
| 发布 | 导出、分享、协作和商业交付 |

资产模式、画布和实时剪辑应是同一领域模型的不同工作界面，不得各自实现生成、素材、保存和计费逻辑。

## 5. 技术架构建议

优先采用模块化单体：

```text
Qiji Desktop / Web
        ↓
统一客户端 SDK 与运行时契约
        ↓
Qiji API 模块化单体
        ↓
项目 / 资产 / 任务 / 计费 / 渠道 / 知识模块
        ↓
PostgreSQL + 对象存储 + 后台任务执行器
```

建议仓库结构：

```text
apps/
  desktop/
  api/
  admin/
  worker/

packages/
  contracts/
  domain/
  client-sdk/
  ui/
  testing/
  config/
```

核心约束：

- 前后端契约由运行时 schema 定义，并生成 TypeScript 类型。
- 商业服务端优先 PostgreSQL；SQLite 可用于桌面本地项目和开发测试。
- 生成任务脱离 HTTP 生命周期，必须持久化、幂等、可取消、可恢复。
- 前端状态按领域拆分，不建立承载整个应用的万能全局 Store。
- 本地文件操作统一经过受控项目存储服务。
- 渠道适配器只负责协议转换，不自行处理计费、资产和任务状态。

## 6. AI 助手总体架构

Qiji 2.0 的 AI 助手采用四层能力架构：

```text
统一的 Qiji AI 助手
        ↓
身份目录与总编排器
        ↓
身份专属 Skill Router
        ↓
Knowledge Retrieval + MCP Tools
```

正式术语：

- **身份 Role**：稳定职责边界，决定谁来处理。
- **Skill**：完成一类任务的方法，决定如何处理。
- **Knowledge**：事实、经验、规则和示例，决定参考什么。
- **MCP Tool**：确定性执行能力，决定实际改变什么。
- **Orchestrator**：拆解任务、选择身份、控制预算和流程。
- **Verifier**：检查结果、约束与交付质量。

身份只是路由与职责边界，不是授权。用户、项目、资源和费用权限必须由 MCP 服务端再次验证。

### 初始身份建议

第一版控制在六个稳定身份：

1. 创作总管。
2. 故事与分镜导演。
3. 视觉与资产导演。
4. 生成制作人。
5. 项目与知识管家。
6. 质量审查员。

根据真实任务数据，再拆分故事编辑、剪辑师、排障专家等身份。身份可以内联执行、使用隔离 Agent，或退化为确定性服务，不应让每个小步骤都启动独立 Agent。

### 身份交付契约

身份之间使用结构化产物协作，例如：

- `StoryRevision`
- `StoryboardPlan`
- `AssetRequirementReport`
- `GenerationPlan`
- `TimelineEditPlan`
- `QualityReport`
- `MemoryProposal`

自然语言用于向用户解释，结构化对象用于角色协作和 MCP 执行。

## 7. MCP 能力层

MCP 工具表达业务动作，不暴露任意数据库、文件和状态修改能力。

建议示例：

- `project.get_summary`
- `project.create_episode`
- `storyboard.generate_draft`
- `asset.search`
- `asset.bind_to_character`
- `timeline.insert_shot`
- `generation.estimate_cost`
- `generation.submit`
- `task.get_status`
- `knowledge.search`
- `memory.propose`
- `memory.commit`

每个工具必须定义输入输出 schema、权限、费用、确认策略、幂等键、撤销能力、影响范围、超时和错误类型。

桌面本地操作建议通过受认证的设备工具代理执行：服务端编排器下发经过校验的工具请求，当前桌面会话执行并返回结构化结果；服务端不直接获得用户整机文件权限。

## 8. 知识、Skills 与用户记忆

### 三类知识

1. 平台知识：模型能力、提示词方法、制作流程、渠道限制、故障排查和官方示例。
2. 项目知识：世界观、角色、场景、时间线、视觉风格、剧情事实和项目决策。
3. 用户知识：跨项目偏好、常用模型、工作流、沟通方式和用户确认过的经验。

项目事实不能污染用户全局偏好；一次性选择不能自动升级为永久记忆。

### Knowledge 与 Skill

- Knowledge 记录“知道什么”。
- Skill 记录“如何完成一件事”。
- Skill 应包含触发条件、输入输出、步骤、工具、权限、依赖知识、验证标准和版本。
- 先检索 Skill/Knowledge 摘要和索引，只读取少量最相关正文，禁止全量注入。

### 检索链

`意图识别 → 作用域过滤 → 索引摘要 → 混合检索 → 重排 → 读取详情 → 去重和冲突检查 → 上下文预算组装`

初期可采用 PostgreSQL 元数据、全文检索和标签；当评测证明有价值时再引入 `pgvector`。

### 用户知识写入

采用两阶段流程：

`memory.propose → 规则判断或用户确认 → memory.commit`

每条记忆保存类型、作用域、来源、置信度、有效期、确认状态和使用记录；用户必须能查看、修改、停用和删除“AI 对我的了解”。

官方签名 Skill 可以指导工具调用；用户知识、项目内容和外部资料不能改变权限、安全规则或费用确认策略。

## 9. 文本模型按 Token 计费

### 已确认方向

- 文本模型由“每次固定收费”改为“按实际 Token 用量计费”。
- 多身份、多步骤分别计量，聚合为用户任务总用量和总费用。
- 用户可追溯模型、步骤、输入 Token、输出 Token、单价和金额。
- 图片、视频和音频计费暂不因本决策改变。
- 编排器必须支持任务级 Token 和金额预算。

### 待定规则

- 输入、输出、缓存、推理 Token 和平台注入上下文分别如何定价。
- Skill、平台知识、项目知识和用户知识的上下文成本如何展示。
- usage 缺失时的可信估算和对账规则。
- 中断、取消、失败、工具错误和重试如何收费。
- 预估、预授权、最终结算、退款和舍入精度。
- 平台价、渠道商价、会员折扣和并行步骤聚合。

详细草案见 [Qiji-2.0-设计需求草案.md](Qiji-2.0-设计需求草案.md)。

## 10. 安全基线

- HTTPS-only，无生产默认凭证。
- 用户、团队、资产和任务采用统一 owner/ACL。
- 外部资源使用高熵 ID，不能依赖不可猜测性代替授权。
- 所有接口运行时校验。
- 计量、扣费、退款和任务状态采用数据库事务与幂等键。
- 严格 SSRF 下载器、上传限制、速率限制和资源预算。
- 管理端采用安全会话和严格 CSP。
- Tauri 采用最小文件、网络和命令权限。
- 密钥加密、轮换和访问审计。
- 敏感信息不进入日志、URL 和对象键。
- 外部知识默认为不可信数据，不能提升权限或改变系统指令。

## 11. 文档与知识体系

- `AGENTS.md`：项目入口导航。
- `CODEX.md`：稳定架构与不可回退规则。
- `ACTIVE.md`：当前阶段、证据、阻塞与下一步。
- `CONTEXT.md` / `CONTEXT-MAP.md`：领域术语和边界。
- `docs/domain/`：领域模型。
- `docs/architecture/`：系统组件与数据流。
- `docs/decisions/`：重要 ADR。
- `docs/handbook/`：开发、测试、发布和排障手册。
- `docs/catalog/`：公共服务、唯一实现入口和复用目录。
- `docs/product/`：目标用户、用户旅程与体验标准。

文档不复制易过期代码细节。长期规则进 CODEX，精确行为由代码和测试证明，当前状态进 ACTIVE，精确历史留给 Git。

## 12. 建设顺序

1. 产品章程、领域术语、架构决策和独立仓库骨架。
2. 运行时契约、错误模型、测试框架、CI 和安全基线。
3. 用户、项目、资产和任务的最小数据模型。
4. 完成第一条端到端闭环：创建项目、添加素材、生成、保存、关闭、重开。
5. 建立 MCP 工具规范、权限和工具测试框架。
6. 建设平台知识库、Skill 索引和只读 AI 助手。
7. 建立渠道适配器框架与 Token/媒体计费事务。
8. 开放带预览、确认和撤销的 AI 写操作。
9. 建设资产工作台、画布和实时剪辑。
10. 建设项目知识、用户知识和多步骤身份编排。
11. 管理端、团队、套餐和商业运营能力。
12. 性能、无障碍、安装升级和公开测试。

## 13. 第一条 AI 验证闭环

建议用以下场景同时验证助手、身份、Skill、知识、MCP、权限、确认和审计：

> 用户询问“我现在下一步该做什么” → 创作总管读取项目摘要 → 检索制作流程 Skill → 给出建议 → 用户确认 → 对应身份调用 MCP 创建缺失任务 → 质量审查员验证 → 返回可撤销结果。

## 14. 主要风险与约束

- 防止完全重写演变为长期没有可运行版本；每阶段必须交付纵向闭环。
- 防止过度抽象；没有第二个真实用例时不建设万能框架。
- 防止身份膨胀和互相转交；保持少量稳定职责并限制委派深度。
- 防止知识库提示词注入；知识与权限严格分层。
- 防止用户记忆积累错误；写入必须有来源、作用域、确认和删除机制。
- 防止 AI 多步骤导致成本失控；任务必须有 Token、金额、时间和工具调用预算。
- 防止文档与代码分叉；关键规则同时由 schema、测试和静态检查约束。
