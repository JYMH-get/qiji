> 一次发版从头到尾的顺序清单，照着做即可。**细节与踩坑**在三个 skill 里，本文只管**顺序、决策点与卡口**：

> - 服务端部署细节 → `.claude/skills/qiji-pack-and-deploy-server/SKILL.md`
> - 客户端打包细节 → `.claude/skills/qiji-pack-client-tauri/SKILL.md`
>
> 项目根：`E:\Kaifa\Qiji\qiji`（换机以实际 clone 位置为准）。

## 阶段 0 · 定发版范围（5 分钟，决定后面跑哪几段）

发版范围**不看本轮，看「上次发版以来累积的所有轮次」**——多轮客户端改动通常攒到同一次发版。

1. 打开 `CLAUDE.md`，从顶部「最后更新」往下翻到上次发版的那一轮，收集每轮结尾的标注：
   - 「**须重新部署服务端**」→ 走阶段 2
   - 「**须客户端重新打包**」→ 走阶段 3
   - 「客户端零改动无需打包」「服务端零改动无需部署」→ 对应阶段跳过
2. 同时记下三件事，后面要用：
   - **本轮部署验证词**（本轮新增的独有字符串，部署后 grep 计数应为 1，CLAUDE.md 里通常已给）
   - **部署后动作**（填上游密钥、填 workflow_id、跑迁移脚本 …）
   - **新增 npm 依赖**（有则服务端部署时要留意 lockfile）

> ⚠ CLAUDE.md 有 500KB+，**只用 Grep 精准查，勿整读**。例如：
> ```bash
> grep -n "须客户端重新打包\|须重新部署服务端" CLAUDE.md | head -20
> ```

**三种发版形态**：

| 形态 | 走哪些阶段 | 说明 |
|---|---|---|
| 只部署服务端 | 0 → 1 → 2 → 4 | 最常见。模式/模型/模板/价格全走 catalog 热更（≤30s），新旧客户端一并生效 |
| 只打客户端 | 0 → 1 → 3 → 5 | 纯前端/Rust 改动 |
| 两者配套 | 0 → 1 → 2 → 3 → 4 → 5 | ⚠ **必须服务端先上线，再分发安装包**（见下方红线） |

## 阶段 1 · 统一自检（不过不许进打包）

按改动面选步骤，不确定就全跑。全部在项目根执行。

| 改动了什么 | 必跑 |
|---|---|
| `server/src/**` | `cd server; npx tsc --noEmit` |
| 客户端 `src/**` | `npx tsc --noEmit`；`npx vitest run`；`npm run build` |
| `server/src/admin/index.html` / `agent/index.html` | **HTML script 语法校验（tsc 零覆盖，漏了=控制台整页白屏）** |
| `src-tauri/**`（Rust） | `cd src-tauri; cargo check` |
| `DEFAULT_SERVER_URL` 等影响产物分支的代码 | build 后 grep dist 实锤 |

- **vitest 基线以 CLAUDE.md 顶部最新轮次为准**（第 254 轮为 **1341**）。数量变了要在结论里写明「1341→N（+M/−M）」，无解释的减少当回归查。
- HTML 校验命令（Git Bash，两个文件都要打印 OK）见 `qiji-preflight-check` 步骤 3。
- 收尾汇总一行实测结论，写进 CLAUDE.md 本轮记录：
  ```
  server tsc 干净 + client tsc 干净 + 1341 vitest 全过 + vite build 过 + admin/agent script 语法过
  ```

> ⚠ 若本轮用本机 dev 8787 做过冒烟：先清 tsx 僵尸进程（8787 上不带 watch 的 `tsx src/index.ts` 永不热重启，冒烟会跑在旧代码上——历史反复踩）。

## 阶段 2 · 服务端打包 + 部署

### 2.1 本机打包（PowerShell 5.1）

```powershell
powershell -ExecutionPolicy Bypass -File E:\Kaifa\Qiji\qiji\server\scripts\pack-deploy.ps1
```

产物落仓库根：`qiji-server-deploy.tgz`。脚本自动剥离 `server\.env` 与 `server\data`（真密钥与生产数据只在服务器维护）。

### 2.2 上传（1Panel 面板）

在 1Panel 文件管理把 `qiji-server-deploy.tgz` 上传到服务器 **`/root`**。

> ⚠ **用户定稿：只走 1Panel 上传，不用 scp**——不要提供、不要建议 scp 方案。

### 2.3 解压 + 构建启动（1Panel 终端）

```bash
tar xzf /root/qiji-server-deploy.tgz -C /opt/qiji
cd /opt/qiji
docker compose up -d --build
```

- ⚠ **`--build` 必带**：不带只是重启旧镜像，新代码完全不生效。
- 本轮有新 npm 依赖时：先 `cd /opt/qiji/server && npm i`，再回 `/opt/qiji` 执行 up --build；并确认本机 `server/package-lock.json` 已更新且已重新打包。

### 2.4 部署验证（三条，全过才算上线）

```bash
# ① 本轮验证词：计数应为 1
grep -c <本轮验证词> /opt/qiji/server/src/<对应文件>

# ② 健康检查（端口只绑 127.0.0.1，公网走 1Panel 反向代理）
curl -s http://127.0.0.1:8787/health

# ③ 首启日志
docker compose logs --tail 100 qiji-server
```

- 验证词 = 0 → 解压/构建没生效（多半是旧包或漏了 `--build`）。
- **首启可能阻塞 1–3 分钟不是挂了**（历史：清存量日志 + VACUUM 2.4GB、39 万行回填），等日志走完再判断。

## 阶段 3 · 客户端打包（Tauri 2）

### 3.1 前置四查（换机/首次打包尤其重要）

```powershell
# ① 三个内置二进制在位（约 186MB，不入 git，缺任一 = 包里缺原生能力）
Get-ChildItem E:\Kaifa\Qiji\qiji\src-tauri\resources -Recurse -File | Select-Object FullName, Length
#   ffmpeg\ffmpeg.exe ≈97MB / libtv\libtv.exe ≈58MB / dreamina\dreamina.exe ≈31MB
#   缺哪个跑哪个（幂等，删 exe 重跑 = 升级版本）：
#   powershell -ExecutionPolicy Bypass -File src-tauri/scripts/fetch-ffmpeg.ps1
#   powershell -ExecutionPolicy Bypass -File src-tauri/scripts/fetch-libtv.ps1
#   powershell -ExecutionPolicy Bypass -File src-tauri/scripts/fetch-dreamina.ps1

# ② 内置深度模型在位（安装包 +45MB）；缺则跑 fetch-depth-model.ps1
Get-ChildItem E:\Kaifa\Qiji\qiji\public\depth-model -Recurse -File | Select-Object Name, Length

# ③ 仓库根无 vite.config.js 残留（必须 False）
Test-Path E:\Kaifa\Qiji\qiji\vite.config.js

# ④ 确认 DEFAULT_SERVER_URL 指向正确服务器（src/store/connectionStore.ts:18）
```

### 3.2 构建 + 产物实锤

```powershell
cd E:\Kaifa\Qiji\qiji
npm run build
```

构建后 **grep dist 实锤打包分支**（Git Bash）：

```bash
grep -l "103.120.91.71:8787" dist/assets/*.js   # 应命中 ≥1（生产分支在）
grep -l "localhost:8787" dist/assets/*.js       # 应无输出（DEV 分支被摇树）
```

换过服务器地址就把 grep 目标换成新地址。**只看 build 成功不算数**——tsc/build 不会告诉你摇树留下的是哪个分支。

### 3.3 打包

```powershell
npm run tauri build
```

（`beforeBuildCommand` 会再跑一次 `npm run build`，属预期。）

### 3.4 取产物并按惯例重命名

- 产物目录：`src-tauri/target/release/bundle/nsis/`（.exe，**实际分发用这个**）与 `bundle/msi/`
- 仓库既有命名惯例：**`Qiji_MMDD.exe`** 或 `Qiji_MMDD-setup.exe`（如 `Qiji_0821.exe`）——原始名是 `Qiji_<version>_x64-setup.exe`，手工重命名后分发。
- 当前包大小参考：≈99MB（第 202 轮内置深度模型后从 ≈55MB 涨上来的，属正常）。

> 版本号说明：`tauri.conf.json` 的 `version` 是 0.1.0、`package.json` 是 0.2.0，客户端内显示的版本取 **package.json**（`src/lib/appVersion.ts`）。版本号常年不 bump，**靠「构建时间」区分新旧包**（个人中心/设置弹窗可见），排查「跑的是哪个构建」时看它。

## 阶段 4 · 部署后动作（服务端上线后立刻做）

按 CLAUDE.md 本轮标注执行，常见三类：

1. **接新渠道的轮次**：管理端「渠道」页填上游密钥；占位配置逐项填齐（如 autodl 的三个 workflow_id）。不填则提交明确报错、不扣费，但功能不可用。
2. **新模型的轮次**：占位价改真价（先小额真单对账再放开，见 `qiji-model-pricing-ops`）。
3. **带迁移/运维脚本的轮次**：
   ```bash
   docker compose exec qiji-server node /app/server/scripts/<脚本>.mjs        # 先看 dry-run
   docker compose exec qiji-server node /app/server/scripts/<脚本>.mjs --apply # 核对无误再真跑
   ```

## 阶段 5 · 真机冒烟（分发前，装包跑一遍）

- 登录页**无**「服务器地址」栏（默认直连生产）；双击 logo 可展开地址栏。
- 真实账号登录成功、积分/模型下拉正常（验证服务端连通与 catalog）。
- **转深度**可用 → 验证 CSP `blob:` 与 WebGPU 参数没被改坏。
- **视频截帧**可用 → 验证 ffmpeg 随包。
- 动过 `capabilities/default.json` 或 `lib.rs`：验证多窗口（二次启动同 exe = 本进程新窗口）不回归。
- 跑一张最便宜的真单，看管理端「请求记录」四段报文正常。

## 顺序红线（一条不能破）

1. ⚠ **服务端先上线，客户端后分发**。客户端新功能常依赖新端点；反过来会让用户拿到「点了报 404」的包。反之只部署服务端一般安全（旧客户端不认新字段但不受影响）——每轮 CLAUDE.md 都会写明「只部署服务端=旧客户端…」的影响面。
2. ⚠ **自检不过不许进打包**。尤其 admin/agent HTML 的 script 语法，tsc 零覆盖，漏检 = 控制台整页白屏。
3. ⚠ **`--build` 必带；上传只走 1Panel；不用 scp**（用户定稿流程，勿自作主张替换）。
4. ⚠ **不改 `productName`（Qiji）/ `identifier`（com.qiji.canvas）**——改 identifier = 换 appData 目录 = 用户数据全丢。品牌改名只动窗口标题与前端资产。
5. ⚠ **仓库根不能残留 `vite.config.js`**——vite 解析 .js 优先于 .ts，会静默遮蔽 `vite.config.ts` 的一切改动（build/vitest 看似过了，跑的却是旧配置）。
6. ⚠ **真密钥绝不进包**：`server/.env` 由打包脚本剥离、`.dockerignore` 双重排除，只在服务器上维护。

## 故障速查

| 现象 | 判据 / 处置 |
|---|---|
| 部署后新功能没生效 | 验证词 `grep -c` = 0 → 旧包或漏 `--build`，重传重构建 |
| 客户端报 404，服务端字段看着正常 | **上传的是旧包**。用「本轮新文件是否存在」一秒判定：`ls /opt/qiji/server/src/store/<本轮新文件>.ts` |
| 容器起不来 | 本轮有新依赖没装（历史：nodemailer / undici / @aws-sdk/s3-request-presigner）；或误用了 `--omit=dev`（tsx 是 devDependency，不能省） |
| 首启卡住很久 | 多半是迁移/VACUUM，看 `docker compose logs` 等它走完，别急着重启 |
| 改了代码本机验证不生效 | 8787 上有不带 watch 的 tsx 僵尸进程，全树清杀后重启 dev |
| 打包版转深度报「no available backend found」 | CSP `script-src` 少了 `blob:`（dev 浏览器复现不出来） |
| 找不到 `/opt/qiji` 的 data 目录 | 那是**容器内视角**路径；宿主机上用 `docker inspect qiji-server` 查 `Mounts` |
