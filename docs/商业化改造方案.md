# 商业化改造方案（渠道商独立部署 · 统一定价 · 免费码 · 注册体系）

> 状态：**计划书（待用户确认，未动代码）**
> 起草：2026-08-09
> 对应需求（用户原话）：
> 1. 渠道商需要能够单独部署，填写源站地址对接源站。
> 2. 源站统一定价，渠道商不再开放模型单独定价（仍然受源站模型开放限制），价格为源站同价。渠道商单独找源站买积分就行。
> 3. 取消开码积分，激活码、团队码，一律免费。
> 4. 取消激活码和机器码系统，升级为用户手机号或者邮箱注册，做好防恶意注册。

---

## 0. 一句话总览

把现在「多租户单体源站 + 双扣费链式结算 + 激活码/机器码」的体系，改造为：

- **源站**：唯一定价方、唯一上游对接方、向渠道商卖积分（池）。
- **渠道商**：可自行部署一台「渠道节点」（同一套服务端软件的 relay 模式），填源站地址+节点密钥即可开张；自己的用户注册在自己节点上，消耗从自己在源站的积分池扣，**价格与源站完全一致**。
- **用户**：手机号/邮箱注册 + 密码登录，无激活码、无机器码。

四条需求不是四个孤立改动，**第 2、3 条合起来是一次经济模型翻转**（见 §3），这是整个方案的核心，必须一次性切换、不能各改各的。

## 2. 目标架构

```
用户A（客户端）──→ 源站（直营用户，平台直属）──→ 各上游 AI 渠道
用户B（客户端）──→ 渠道节点（渠道商自部署，relay 模式）──┐
                     · 自己的用户库/注册/团队/日志          │ 凭 nodeKey 走 /v1 协议
                     · 消耗按平台价扣本地用户积分            ↓
                     · 请求原样转发源站 ────────────→ 源站（按平台价扣该渠道商积分池）──→ 上游
```

要点：

- **客户端零改动即可接渠道节点**——客户端本就允许填任意服务器地址（`connectionStore.serverUrl`），渠道节点对客户端暴露的就是同一套 `/v1` 协议。
- **同一套服务端代码，两种角色**：env 配 `NODE_ROLE=source`（缺省，现行为）或 `NODE_ROLE=relay`（+ `SOURCE_URL` + `SOURCE_NODE_KEY`）。relay 模式不加载翻译器/渠道/上游密钥，dispatch 一律转发源站。
- **对账天然成立**：源站给渠道节点的每笔转发请求记日志（ownerId=该商），渠道节点本地也有自己的用户日志——两边数字可互相核对。

## 3. 改造一：经济模型翻转（需求 2 + 3，必须同时切换）

### 3.1 为什么必须一起改

现状的经济闭环是：渠道商发码**免费铸造**用户积分面额（兑换码签发不扣、激活码只扣「开码费」不扣面额），代价在**用户每次消耗时**通过链式进货价结算收回。如果只做「统一定价+免费码」而不动结算，渠道商成本归零；如果只取消链式结算而面额仍免费铸造，渠道商可以**无限给自己用户发积分**白嫖源站。所以切换必须是一个原子包：

| | 旧模型 | 新模型 |
|---|---|---|
| 用户消耗 | 扣用户（渠道商售价）+ 渠道商链逐级扣（进货价） | **只扣用户（平台统一价）** |
| 渠道商成本 | 每请求按进货价被动扣 | **预购积分池，给用户发积分时实扣**（发多少扣多少） |
| 渠道商利润 | 售价−进货价 的差价 | 卖积分给用户的溢价（体外收款，系统内 1:1 划转） |
| 开码费 | 按有效期档扣开码积分 | **取消** |

### 3.2 具体改动（服务端）

1. **planBilling / chargeBilling**（`routes.ts:139-192`）：删掉 `agentChain(...)` 进货价段，`settle()` 的 `agents` 恒为空数组；402 文案不再出现「渠道商积分不足」。退款（同步失败/异步钩子/启动对账）同步只退用户侧。`logs.agentCosts` 停写（字段留档兼容历史记录展示）。
2. **catalog 去换价**（`catalog.ts:211-238`）：删 `effectiveSalePricing` 调用，价格恒为平台 `ModelDef.cost/costPerUnit/costRules`；`chainPricingVersion` 段从 catalog version 中退役（保留一个恒定段位防旧客户端 version 解析错位）。**模型开放范围过滤原样保留**（`modelAllowedForAgent`，catalog.ts:205-209）。
3. **分发实扣**：渠道商给用户发积分的全部入口改为「从渠道商 `credits` 池真实划转」：
   - 兑换码签发（`/agent-api/redeem-codes`）：签发即按**面额×数量**扣池，作废未用退回；核销把面额记给用户（现有 `grantCredits` 不变）。
   - 门户直充用户（如后续需要）走同一原语。
   - 源站（admin）签发/直充仍是发行方，不扣自身——与现状一致。
4. **开码积分整体退役**：`codeCredits` 字段停用，**存量余额直接清零舍弃**（迁移脚本备份 agents.json 留档，不并入通用积分——已拍板）；`planCodeIssue/applyCodeIssue/transferAgentCodeCredits/changeAgentCodeCredits` 及其端点、门户「开码积分」卡与划转 UI 全删；`logCodeIssue` 保留（免费签发也要留痕，cost=0）。
5. **团队码免费且仅源站签发**：`getTeamCodePrice` 退役（settings 键废弃）；**门户团队码签发/删除端点整删**（`/agent-api/team-codes*`），源站 `/admin-api/team-codes` 保留（免费、留痕）；门户「名下团队」只读表保留。
6. **扩容卡机制原样保留**：签发流程/规格配置/核销全部不动，仅因开码积分废除而**签发免费**；是否收费留待后续升级再议。
7. **门户瘦身**（`routes/agent.ts` + `agent/index.html`）：删 模型定价/改价/进货价/签发价/默认下级价目/开码积分/团队码签发/**下级商管理（sub-agents 全组）** 页面与端点；保留 概览（余额/用量）、用户管理、兑换码（实扣）、扩容卡、名下团队只读、请求记录、统计、模型只读（可见性+显示名+本商启停）。
8. **多级链拍平**：`agentChain/chainPricingVersion/CHAIN_MAX` 等链式逻辑退役；存量下级商一次性迁移为源站直连（`parentAgentId` 清空留档进备份），此后所有渠道商平级、统一由源站管理端管理与充值。
9. **数据迁移**：一次性脚本备份 agents.json 后——剥离 `modelPricing/costPricing/codePricing/codeSalePricing/defaultSub*` 定价字段（防幽灵生效）+ `codeCredits` 清零 + `parentAgentId` 拍平，三件事一个脚本完成、dry-run 先行。

### 3.3 客户端影响

**零改动**。价格经 catalog 下发，客户端预估（`genParams.ts estimateCost`）自动跟随平台价；积分余额/402 语义不变。

## 4. 改造二：注册体系（需求 4）

### 4.1 注册/登录流程

- **注册**：`POST /v1/register/send-code`（邮箱或手机号 + 图形验证码）→ 收 6 位验证码 → `POST /v1/register`（账号=邮箱/手机号、验证码、密码、昵称）→ 直接建号（源站=平台直属；渠道节点=该商用户）→ 自动生成 accessKey 返回，客户端存储后与现状完全一致。
- **登录**：账号（邮箱/手机号）+ 密码，复用现有 `loginWithAccount` 机制（`routes.ts:263-289`），**删除 bindOrCheckMachine 一步**。
- **找回密码**：`POST /v1/password/send-code` + `POST /v1/password/reset`（验证码重置）——商业软件必备，本次补齐（现状只能管理端重置）。
- 旧的激活码注册端点 `POST /v1/register`（绑激活码语义）替换为新语义；批量激活码端点（admin/agent 两处）下线。

### 4.2 验证码通道

- **邮箱（P2 必做）**：SMTP 直发（nodemailer），配置在管理端 settings（host/port/user/pass/发件人），管理端可发测试邮件自检。
- **手机号（可插拔，配置后启用）**：短信适配器接口 + 阿里云短信实现（AccessKey/签名/模板 code 配置在 settings）。⚠ 前提：短信需企业资质 + 签名/模板审批，且按条计费——代码先就位，**未配置时注册页只显示邮箱通道**，配置后自动出现手机号通道。

### 4.3 accessKey 的去留

**保留但降级**：accessKey 从「激活码（对外分发的凭证）」降级为「注册时自动生成的内部 API 凭证」，仍是全部 `/v1/*` 的 Bearer——这样 `requireAccessKey`、心跳、任务轮询、台账、日志全链路零改动。用户永远看不到它（登录换取、客户端静默持有），个人中心保留「重置凭证」（顶掉其它已登录端）。

### 4.4 防恶意注册（防线清单）

| 防线 | 参数（管理端可配） |
|---|---|
| 图形验证码 | send-code 前置（自绘 SVG 算术/字符码，无第三方依赖） |
| 发码频控 | 同账号 60s 冷却；同 IP 10 次/小时、20 次/天 |
| 验证码 | 6 位数字，10 分钟 TTL，5 次错误作废 |
| 注册频控 | 同 IP 5 户/天（可配）；同邮箱/手机号唯一 |
| 一次性邮箱 | 内置常见临时邮箱域黑名单 + 管理端可增删 |
| 注册开关 | 全局开/关；可选「邀请码模式」（关时仅凭邀请码注册，留作运营阀门） |
| 注册赠送 | **默认 0，机制保留可配**（为后续邀请码/运营活动预留）；配置 >0 时代码联动强制开启图形验证码并收紧 IP 限额 |

频控计数存 SQLite（`qiji.db` 新表 `reg_guard`），重启不丢。

### 4.5 机器码退役与「同时在线」限制（已拍板：不限机器，限同时在线，默认 1 台）

- 服务端：`auth.ts requireAccessKey` 删机器码**绑定**校验；`users.ts bindOrCheckMachine` 退役；`machineCode` 字段留档。
- 客户端：**继续采集并发送 `x-machine-code` 头**（新服务端拿它当设备标识、旧服务端仍校验绑定——双向兼容的关键，勿删采集代码）；登录页删机器码展示、注册页删激活码字段。
- **同时在线限制（登录抢占制）**：
  - 服务端按账号维护「活跃设备表」（新表 `user_devices`：deviceId=机器码头、lastSeenAt）；上限=全局默认 **1**（管理端可配全局值 + 按用户覆盖）。
  - **登录即抢占**：新设备账号密码登录成功 → 成为活跃设备；被顶掉的旧设备后续请求/心跳收到 403「已在其它设备登录」→ 客户端既有「401/403 立即登出」逻辑自然生效，无需新增客户端代码路径。
  - 同一台机器多开窗口=同一 deviceId，不占多个名额；换机无需解绑（登录即换）。
  - 上限 >1 时按 LRU 语义：超限登录顶掉最久未活跃的设备。

### 4.6 存量用户迁移

- 已有账号密码的用户：**无感**——登录照旧，只是不再校验机器码。
- `validityDays/expiresAt` 存量到期语义：已写入的继续生效到期（已售出的商品不追溯），新体系不再产生（§8-Q7）。
- 旧打包客户端：登录可用（服务端忽略其机器码头）；其「注册」页（要激活码）自然失效——引导升级新版客户端。

## 5. 改造三：渠道商独立部署（需求 1，relay 模式）

### 5.1 源站侧（对接面）

1. `Agent` 新增 `nodeKey`（`ank-` 前缀随机密钥），源站管理端「渠道商详情」生成/重置/展示对接指引。
2. `/v1/*` 鉴权扩展：Bearer 为 `ank-` 时解析为渠道节点身份（`req.agentNode`），要求该商 enabled。**计费分支**：`planBilling` 对节点请求「付款人=该商 credits 池，平台价，无用户侧」；日志 `ownerId=该商`、`userId` 记节点转发来的本地用户标识（仅留痕）。
3. 节点可用端点：`catalog`（按该商开放范围过滤，平台价）、`generate/batch/tasks`、`assets`（上传/直传签发/raw）、`assets/ref`（引用上报透传，保住保留策略语义）、新增轻量 `GET /v1/node/me`（池余额/enabled/名称——节点管理端展示源站余额）。
4. 渠道商门户保留但瘦身为：概览（池余额/用量）+ 请求记录 + 节点密钥管理。

### 5.2 渠道节点侧（relay 模式）

- **启用方式**：`.env` 配 `NODE_ROLE=relay` + `SOURCE_URL` + `SOURCE_NODE_KEY`，其余零配置可跑（**不需要配 OSS、不需要任何上游密钥**）。
- **本地拥有**：用户库（注册体系 P2 全套）、团队、兑换码（本地积分经济，自主发行——超发风险自担：本地铸多了、源站池扣穿即 402，见 5.3）、请求日志、注册/频控设置。
- **转发层**（替换 dispatchGenerate）：
  - `catalog`：定时拉源站 catalog（带 since 缓存），可叠加本地「模型启停」再下发给自己的用户；模板/预设随 catalog 透传（正文本就不下发，保密语义不变）。
  - `generate`：先扣本地用户积分（平台价，源站 catalog 即计价依据）→ 转发源站（素材已是公网 URL，原样透传）→ 源站扣池；源站 402/失败 → 本地退款。异步任务：本地任务记录镜像源站 taskId，轮询转发。
  - `assets`：上传转发源站（multipart 或直传签发透传）；`/v1/assets/:id/raw` 302 到源站同路径（公开端点）。
  - `assets/ref`：本地用户的引用上报聚合后转发源站——**渠道节点用户的素材同样受源站保留策略保护**。
- **本地管理端**：现有 `/admin` 复用，relay 模式隐藏 模型/渠道/模式/家族/模板/预设/存储(OSS) 等源站专属页，保留 用户/团队/兑换码/请求记录/统计/注册设置，另加「源站连接」卡（地址/余额/连通性自检）。
- **计费一致性**：节点本地价 = 源站 catalog 下发价，同一份数据两边各扣一次（本地扣用户、源站扣池），金额恒等——对账即「本地日志合计 vs 源站该商 ownerId 日志合计」。

### 5.3 信任边界（设计立场，写进文档不写进代码）

渠道节点的本地积分是**自主发行**的（节点管理员想给自己用户发多少都行），源站不管、也管不着——源站的守门员只有一个：**该商积分池**。池扣穿了，节点的一切转发请求 402。这把「渠道商超卖」变成纯粹的商务问题而非技术漏洞，也免去两边同步用户账本的复杂度。

## 9. 风险

1. **P1 是经济语义切换，无灰度**——切换瞬间前后两套账并存于历史日志（旧日志有 agentCosts、新日志没有），统计页需按时间口径解释清楚；上线前必须沙盒全量冒烟 + 备份 agents.json/users.json/qiji.db。

3. **relay 转发链路的双写一致性**——本地扣款成功、转发源站前进程崩溃：本地任务表落盘 + 启动对账（复用第 89 轮模式）补态/退款；此路径 P3 必须有专项测试。
4. **合规提示**（点到为止）：手机号注册涉及短信实名链路；对外商用建议确认 ICP 备案/软著/隐私政策文案（客户端注册页需挂用户协议与隐私政策链接，P2 预留占位）。
